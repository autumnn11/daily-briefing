# 관심 단지·구역 실거래 일일 브리핑 — 설계

작성일: 2026-09-29
상태: 설계 확정, 구현 계획 대기

## 1. 목적과 성공 기준

전업투자자가 매주 손으로 하던 부동산 확인 작업을 매일 자동으로 돌려 Slack으로 받는다.

대체 대상 (사용자가 지난주 실제로 한 일):

- 관심 재개발 구역에 실제 나오고 있는 매물 확인
- 구역 내 빌라 거래건 확인
- 관심 아파트 단지 실거래 확인
- 지역별 전/월세·매매 매물 증감 확인

**성공 기준**: 30일 뒤, 아침에 Slack만 열면 위 네 가지 확인이 이미 끝나 있다. 사용자가 손으로 사이트를 돌아다니는 시간이 0이 된다.

**형식 기준**: `stock.png`(월스트리트나우 형식 카드 브리핑) 수준의 밀도. 숫자 나열이 아니라 "오늘 볼 게 있나"를 3초 안에 판단할 수 있는 한 장.

## 2. 범위

### 한다

- 국토부 실거래가 공개 API로 체결 거래 수집 (아파트 매매, 연립다세대 매매)
- 네이버부동산 호가 매물 수집 (`vendor/anti_bot_scraper`)
- 전일 대비 신규/소멸/가격변동 대조
- HTML 카드 렌더 → PNG → Slack 발송
- Windows 작업 스케줄러 등록

### 안 한다 (이번 30일 범위 밖)

- 부동산 뉴스·정책 헤드라인 수집
- 재개발 구역 행정 고시·공고 감시
- 등기부등본 열람 (건당 결제 + 본인인증 필요)
- 중개사 연락처 수집·보관 (10절 참조)
- 매수·매도 추천이나 의사결정. 이 시스템은 사실만 나른다

## 3. 관심 목록 — `watchlist.yml`

두 수집기가 지역을 서로 다른 방식으로 받는다. 국토부는 시군구 코드(`LAWD_CD` 5자리) + 연월만 받고, 네이버 스크레이퍼는 지도 좌표(lat/lon/zoom)만 받는다. 따라서 대상 하나에 주소를 두 벌 적는다.

**재개발 구역 처리 방침 — 법정동 단위.** 국토부 데이터에는 "구역" 개념이 없어 구역 안팎을 구분할 수 없다. 구역 경계 지번을 조사해 넣는 대신, 국토부 쪽은 법정동 전체를 보고 구역 정밀 조준은 네이버 호가 쪽이 좌표로 담당한다. 구역 주변 시세가 같이 보이는 것은 손실이 아니라 이득으로 본다.

```yaml
수도권:
  - 이름: 장위 재개발 일대
    유형: 구역
    lawd_cd: "11290"              # 성북구
    법정동: ["장위동"]             # 국토부 응답을 이 법정동으로 필터
    좌표: {lat: 37.6130, lon: 127.0480, zoom: 17}
    자산: "VL"                    # 네이버: 빌라
  - 이름: 래미안장위
    유형: 단지
    lawd_cd: "11290"
    법정동: ["장위동"]
    단지명: "래미안장위"           # 국토부 응답을 단지명으로 추가 필터
    좌표: {lat: 37.6142, lon: 127.0501, zoom: 17}
    자산: "APT"

지방:                              # 온도계용, 지역별 대장 1개
  - 이름: 대전 둔산 크로바
    lawd_cd: "30170"
    법정동: ["둔산동"]
    단지명: "크로바"
```

좌표는 네이버지도에서 우클릭 → URL 복사로 얻는다. `수도권` 항목만 네이버 수집 대상이며, `지방` 항목은 국토부만 조회한다(대장 아파트는 호가 감시 대상이 아니라 추세 지표다).

watchlist가 비어 있어도 파이프라인은 정상 동작해야 한다 — "감시 대상 없음" 브리핑을 보낸다.

## 4. 데이터 출처

### A. 국토부 실거래가 공개 API (공공데이터포털)

- 사용 오픈API: "국토교통부_아파트 매매 실거래가 자료", "국토교통부_연립다세대 매매 실거래가 자료"
- 파라미터: `serviceKey`, `LAWD_CD`(시군구 5자리), `DEAL_YMD`(YYYYMM)
- 인증키는 사용자가 data.go.kr에서 직접 발급(무료). `.env`에 보관
- **정확한 오퍼레이션 경로와 응답 필드명은 구현 1일차에 실호출로 확정하고 `docs/api-notes.md`에 실제 응답 샘플과 함께 기록한다.** 이후 코드는 그 문서를 근거로 작성한다
- **핵심 제약**: 응답에 "신고일" 필드가 없다. 조회는 계약년월 단위다. 따라서 "오늘 새로 올라온 건"은 API가 알려주지 않으며, 전일 스냅샷과의 대조로만 구한다
- 신고 기한이 계약 후 30일이므로 매일 **최근 3개월치**를 전부 재조회한다

### B. 네이버부동산 호가 (`vendor/anti_bot_scraper`)

- MIT 라이선스, Playwright 기반. `scraper_kr.py`의 `crawl_detailed(lat, lon, zoom)`을 직접 호출한다
- `main()`은 쓰지 않는다 — `input()`으로 좌표를 물어 스케줄러에서 실행 불가
- 결과를 반환하지 않고 실행 디렉터리에 `매물정보_확장_YYYYMMDD_HHMMSS.xlsx`를 쓴다. 래퍼가 임시 디렉터리에서 실행한 뒤 생성된 xlsx를 읽고 삭제한다
- **반드시 덮어써야 하는 모듈 상수**:
  - `ONLY_PREV_GT_SALE = False` (기본 True. 그대로 두면 직전 전세가 ≥ 매매가인 갭투자 후보만 남아 구역 매물 대부분이 사라진다)
  - `ONLY_WITH_PREV_JEONSE = False` (같은 이유)
  - `DETAIL_WORKERS = 4` (기본 12. 매일 도는 자동화에는 과하다)
  - `ASSET_TYPES` = watchlist 항목의 `자산` 값
  - `MAX_COMPLEX_DETAIL = 100`, `MAX_ARTICLE_DETAIL = 1500` (구역 단위 조회에 맞춰 축소)
- 구역 사이에 5~15초 랜덤 지연을 넣는다
- 갭 지표(`갭금액`, `갭비율`, `기전세금`)는 필터가 아니라 표시 항목으로만 쓴다

## 5. 데이터 모델 (SQLite, `data/briefing.db`)

### `trades` — 체결 거래

- 키: `trade_hash` = SHA1(`lawd_cd`, `법정동`, `단지명`, `계약일`, `전용면적`, `층`, `거래금액`)
- 컬럼: 위 구성요소 + `거래유형`(중개/직거래), `해제여부`, `해제사유발생일`, `등기일자`, `자산유형`(APT/VL), `first_seen`(DATE), `last_seen`(DATE)
- 신규 판정: 오늘 조회분에 있는 `trade_hash`가 테이블에 없으면 신규
- 파기 판정: 기존 행의 `해제여부`가 오늘 조회분에서 바뀌었으면 파기

### `listings` — 호가 매물 (현재 상태)

- 키: `매물번호`
- 컬럼: `매물명`, `거래유형`, `가격`, `층수`, `면적`, `전용면적`, `방향`, `특징`, `등록일`, `기전세금`, `갭금액`, `갭비율`, `구역명`, `first_seen`, `last_seen`
- 소멸 판정: `last_seen`이 어제이고 오늘 조회분에 없으면 소멸

### `listing_price_history` — 호가 가격 이력

- `(매물번호, 관측일, 가격)`. 같은 매물번호의 가격이 직전 관측과 다를 때만 행을 추가한다
- 가격 조정 판정의 근거. 조정폭과 조정까지 걸린 일수를 여기서 계산한다

### `runs` — 실행 로그

- `실행일시`, `단계`(kor_api/naver/render/slack), `성공여부`, `수집건수`, `소요초`, `오류메시지`
- 30일 뒤 "며칠이나 제대로 돌았나"를 이 테이블로 평가한다

## 6. 일일 실행 순서

매일 08:00 (Windows 작업 스케줄러). PC가 꺼져 있었으면 다음 부팅 시 밀린 분을 실행한다.

1. **국토부 수집** — watchlist의 고유 `lawd_cd`별로 아파트매매·연립다세대매매를 최근 3개월치 조회. 실패 시 3회 재시도(지수 백오프)
2. **`trades` 적재 + 대조** — 신규 건, 파기 건 산출
3. **네이버 수집** — `수도권` 항목만 순차 실행. 항목 사이 랜덤 지연. 이 단계 실패는 파이프라인을 중단시키지 않는다
4. **`listings` / `listing_price_history` 적재 + 대조** — 신규 등록, 소멸, 가격 조정 산출
5. **판정** (7절 규칙 적용)
6. **HTML 렌더 → PNG** (Playwright `page.screenshot`, 스크레이퍼가 이미 설치하므로 추가 의존성 없음)
7. **Slack 발송** — PNG 업로드 + Block Kit 텍스트 요약

각 단계는 독립 실행 가능해야 한다. 특히 `render.py 2026-09-28` 형태로 **네트워크 없이 과거 날짜 브리핑을 다시 뽑을 수 있어야 한다** — 30일 동안 형식을 다듬는 주된 수단이다.

## 7. 판정 규칙

### 신고가 / 하락 판정

- 비교 대상: **같은 단지 + 같은 전용면적**, **최근 1년(365일) 계약일** 범위 내 최고가
- 오늘 신규 건의 거래금액이 그 최고가를 넘으면 `▲ 신고가`, 밑돌면 `▼ -N%`
- 비교 대상이 되는 과거 거래가 3건 미만이면 판정을 붙이지 않고 `비교 표본 부족`으로 표시한다. 1~2건으로 신고가를 외치면 오판이 잦다

### 특이사항 뱃지

가격 판정을 오염시키거나 해석에 필요한 요소를 카드에 뱃지로 붙인다.

- `1층` / `2층 이하` — 같은 평형이라도 원래 낮게 거래된다
- `최상층` — 단지에 따라 프리미엄 또는 디스카운트
- `직거래` — `거래유형`이 중개가 아닌 건. 특수관계 거래 가능성
- `해제` — `해제여부`가 설정된 건
- `미등기` — 계약 후 60일 넘도록 `등기일자`가 비어 있는 건

### 거래량 (지방 온도계)

- 대장 단지별 **월별 거래 건수** 최근 3개월 + **전년 동월 대비**
- 가격보다 거래량이 먼저 움직이므로 온도계의 주 지표로 쓴다
- 함께 표시: 최근 3개월 평당가 추세(%), 최근 1년 최고가 대비(%)

### 가격 조정 (호가)

- `listing_price_history`에서 직전 관측 대비 가격이 내려간 매물을 뽑는다
- 표시: 조정폭(원, %), 직전 가격, 등록 후 경과일, 누적 조정 횟수
- **누적 조정 2회 이상**인 매물은 별도로 강조한다. 반복해서 내리는 건 매도 의지가 강하다는 신호다
- 가격이 오른 매물도 같은 섹션에 표시하되 구분한다

## 8. 브리핑 구성

`stock.png`의 카드 구조를 따른다. 섹션 여섯 개.

1. **헤더** — 날짜 + 한 줄 요약 (그날 가장 큰 사건 하나)
2. **오늘의 스냅샷** — 신규신고 / 신규매물 / 소멸매물 / 가격조정 / 계약파기, 숫자 5칸. 전부 0이면 "오늘은 조용합니다" 한 줄로 축약
3. **수도권 상세** — 신규 체결 거래 카드. 금액, 전용면적, 층, 계약일, 신고가/하락 판정, 특이사항 뱃지
4. **호가 동향** — 구역별 매물 수 증감, 신규 등록, 소멸, 최저 호가
5. **가격 조정** — 내린 매물 목록(조정폭·경과일·누적 횟수), 오른 매물은 구분 표시
6. **지방 온도계** — 대장 단지별 월별 거래량 + 전년 동월 대비 + 평당가 추세 + 전고점 대비

하단에 수집 상태 배너(어느 단계가 실패했는지)와 데이터 기준 시각을 찍는다.

## 9. 실패 처리

- **국토부 API 실패** — 3회 재시도 후 포기. 브리핑 상단에 경고 배너, 전일 데이터 기준임을 명시
- **네이버 차단 감지** — 즉시 중단, 해당 항목 스킵, 기존 `listings`의 `last_seen`을 갱신하지 않는다(소멸로 오판하면 안 됨). 브리핑에 "호가 미수집" 표시
- **둘 다 실패** — 그래도 Slack에 메시지는 보낸다. "오늘 수집 실패 + 사유"가 오는 것이 아무것도 안 오는 것보다 낫다
- **렌더 실패** — PNG 없이 Block Kit 텍스트만 보낸다
- **Slack 실패** — 로컬에 PNG와 HTML을 남기고 `runs`에 기록. 다음 실행에서 밀린 건을 함께 보낸다

모든 실패는 `runs`에 남긴다.

## 10. 개인정보 및 법적 취급

- 스크레이퍼 출력의 `부동산상호`, `중개사이름`, `전화1`, `전화2` **네 컬럼은 DB 적재 전에 버린다.** 원본 xlsx도 읽은 직후 삭제한다. 매물 판단에 쓰지 않는 값이며, 중개사 개인 연락처에 해당한다
- 수집 용도는 사용자 본인의 투자 판단에 한정한다. 제3자 제공, 재배포, 상업적 이용을 하지 않는다
- 네이버 서비스 약관상의 위험은 사용자에게 있음을 인지한 상태에서 진행한다. 레포의 "교육·연구 목적" 면책은 약관을 면제하지 않는다
- 동시 워커 축소, 구역 단위 소규모 조회, 1일 1회 실행, 랜덤 지연으로 부하를 최소화한다
- 차단이 발생하면 재시도하지 않고 그날은 포기한다. 우회를 강화하는 방향으로 대응하지 않는다

## 11. 준비물 (사용자가 직접)

1. **공공데이터포털 인증키** — data.go.kr 가입 → 실거래가 오픈API 활용신청 (무료)
2. **Slack 봇 토큰** — 본인 워크스페이스에 앱 생성, 스코프 `chat:write` + `files:write`, 발송 채널에 봇 초대
3. **watchlist 내용** — 관심 구역·단지와 좌표

1·2는 `.env`에 넣고 `.gitignore`로 제외한다. 저장소에 올리지 않는다.

| 1주 | watchlist + 국토부 수집 + `trades` 대조 + Slack 텍스트 발송 | 주말에 첫 Slack 메시지가 자동으로 온다 |
| 2주 | 판정 규칙(신고가·뱃지) + HTML 카드 + PNG 렌더 | 이미지 형태로 온다 |
| 3주 | 스크레이퍼 래퍼 + `listings` + 가격 이력 + 호가/가격조정 섹션 | 호가 동향이 붙는다 |
| 4주 | 지방 온도계, 실패 처리, 작업 스케줄러 등록, 형식 다듬기 | PC만 켜두면 알아서 온다 |

1주차 끝에 이미 매일 무언가 도착하도록 순서를 짰다. 이후 3주는 그 위에 얹는 작업이다.

## 13. 기술 스택

- Python 3.11+
- 수집: `requests`(국토부), `playwright`(네이버, 렌더 공용)
- 저장: `sqlite3` (표준 라이브러리)
- 데이터: `pandas`, `openpyxl` (스크레이퍼 출력 읽기)
- 설정: `pyyaml`
- 발송: `slack_sdk`
- 템플릿: `jinja2`

## 15. 테스트 방침

- 국토부 API 응답과 스크레이퍼 xlsx를 고정 픽스처로 박고, `store.py`의 대조 로직과 `judge.py`의 판정 규칙을 네트워크 없이 검증한다
- 대조 로직 검증 항목: 신규 건, 재조회 시 중복 미생성, 파기 감지, 소멸 감지, 가격 조정 감지, 네이버 실패 시 소멸 오판 방지
- 판정 규칙 검증 항목: 1년 창 경계, 표본 3건 미만, 1층·최상층 뱃지, 직거래·해제·미등기 뱃지, 전년 동월 대비 계산
- `render.py`는 픽스처 DB로 PNG를 생성해 눈으로 확인한다
